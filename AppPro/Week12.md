# 앱프로그래밍기초 12주차 배운 내용 정리

## 1. 개발 규칙과 자동화
- **개발 규칙(Guideline)** : 코드의 일관성·가독성·유지보수성을 위해 지키는 기준
- 규칙은 막연한 취향보다 **언제 적용하고 어떻게 확인할지** 명확해야 함
- 반복해서 확인할 수 있는 규칙은 분석·형식 검사·테스트로 자동화
- 규칙을 정할 때 현재 앱의 요구사항과 개발 범위를 우선 고려

## 2. Effective Dart
- Dart 코드의 작성 방식을 다루는 공식 가이드
- **Style** : 코드의 표기·형식
- **Documentation** : 주석과 API 설명
- **Usage** : 언어·라이브러리 사용 방법
- **Design** : 라이브러리와 API를 설계하는 방법
- 모든 규칙을 무조건 복사하기보다 프로젝트에 필요한 기준을 선택하고 이유를 기록

## 3. 포매터·린터·테스트의 역할
- **Formatter(포매터)** : 일관된 코드 형식으로 정리
- **Linter(린터)** : 코딩 규칙과 문제가 될 수 있는 패턴 점검
- **Analyzer(분석기)** : Dart 코드의 정적 오류와 경고 확인
- **Test(테스트)** : 작성한 검증 코드로 예상 동작 확인
- **직접 실행** : 실제 화면에서 입력·행동·결과 확인
- 형식 검사가 통과했다고 기능이 올바르게 작동한다는 뜻은 아님

## 4. 분석 규칙 설정
- **analysis_options.yaml** : Dart·Flutter 프로젝트의 정적 분석 및 린트 규칙 설정 파일
- 프로젝트의 공통 분석 기준을 지정하고 필요에 따라 규칙을 추가·조정
- 규칙을 무조건 무시하기보다 경고 이유와 수정 범위를 먼저 확인
- 규칙 변경도 코드와 함께 검토하고 기록

## 5. 자주 사용하는 검사 명령어
```powershell
dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test
flutter devices
flutter run
```

- `dart format` : 코드 형식 검사 또는 형식 정리
- `flutter analyze` : 정적 분석
- `flutter test` : 작성된 테스트 실행
- `flutter devices` : 실행할 장치 확인
- `flutter run` : 앱 실행과 실제 동작 확인
- 테스트가 없거나 실행하지 못했다면 **테스트 없음 / 미실행** 등으로 정확히 기록

## 6. 요구사항·정책·절차·현황 구분
- **PRD.md** : 앱이 무엇을 제공해야 하는지와 인수 조건(AC)
- **정책 파일** : 코드를 수정할 때 지속적으로 지킬 규칙
- **스킬(Skill)** : 특정 작업을 반복 수행하는 절차
- **IMPLEMENTATION.md** : 실제 구현·확인 상태와 남은 작업
- 만들고 싶은 기능과 실제 구현된 결과를 다른 문서에서 구분하여 관리

## 7. Antigravity와 AI Agent
- **Antigravity** : 프로젝트 파일과 코드를 연결하여 AI Agent와 개발 작업을 진행하는 도구
- App 또는 IDE에서 기존 Flutter 프로젝트 폴더를 연결하여 사용
- `@` 파일 지정 기능으로 PRD나 관련 코드를 작업의 참고 자료로 전달
- AI Agent는 파일 조사·계획·수정·검증을 도울 수 있지만 실제 변경 내용과 실행 결과는 직접 검토
- 첫 요청은 **PRD와 코드의 차이 확인 → 계획 제안**으로 작게 시작

## 8. 프로젝트 정책 파일
- **GEMINI.md / AGENTS.md** : 프로젝트의 공통 작업 기준과 제약을 적는 정책 문서
- 이미 정책 파일이 있으면 별도 파일을 중복 생성하기보다 먼저 확인
- 요구사항 확인·변경 범위·검사 명령·결과 기록 방법 등을 명시
- **.agents/rules/*.md** : 필요 시 별도 규칙을 저장할 수 있는 위치
- 문서상의 규칙과 도구의 실제 파일 접근·실행 권한 설정을 구분

## 9. Agent Skill
- **Skill** : 반복해서 수행할 작업의 입력·절차·확인 방법을 문서화한 것
- 예 : `.agents/skills/prd-check/SKILL.md`
- `SKILL.md`에 이름·설명과 검사·기록 절차 작성
- **정책**은 지속해서 지킬 원칙, **스킬**은 특정 상황에서 따를 작업 순서
- 스킬을 만들었다는 사실과 실제로 적용하여 검증했다는 사실을 구분

## 10. PRD 대조와 작은 기능 구현
1. PRD에서 **요구사항 ID와 인수 조건** 확인
2. 현재 코드의 관련 파일과 동작 조회
3. **차이·변경 범위·검증 방법**을 작은 계획으로 정리
4. 해당 사용자 행동 한 가지만 구현
5. 변경한 코드와 실제 실행 결과 비교
6. 남은 요구사항과 다음 작업 기록
- AI가 계획 밖의 큰 구조 변경이나 불필요한 패키지를 추가하는지 확인
- 실제 실행하지 않은 기능을 완료로 처리하지 않음

## 11. 구현 현황 문서
- **IMPLEMENTATION.md** : 현재 기능의 구현·검증 상태를 별도로 기록
- **미구현 / 구현·미검증 / 확인 완료 / 실패 / 미실행** 등으로 상태 구분
- 요구사항 ID, 관련 코드, 확인한 입력·동작·결과, 실행 장치, 날짜 기록
- 오류 로그나 화면 캡처가 있다면 위치와 함께 남기기
- PRD의 요구를 실제 구현에 맞춰 임의로 줄이지 않음

## 12. 중간발표와 개발 피드백
- 12주차에는 **1~3쪽 중간발표**로 앱 주제·문제·핵심 가치와 15주차 목표 설명
- 피드백은 **확인할 질문 / PRD 반영 사항 / 이번에 반영하지 않을 의견**으로 구분
- 발표 자료의 목표와 현재 구현된 결과를 분명하게 분리
- 이후 개인 프로젝트에서 선택한 행동 하나를 구현하고 검증

## 13. 핵심 정리
- 코드 품질 관리에는 **명확한 규칙과 반복 가능한 검증**이 필요
- 포매터·분석기·테스트·직접 실행은 각각 확인하는 대상이 다름
- **PRD(목표) / 정책(규칙) / 스킬(절차) / 구현 현황(실제 결과)**을 구분
- Antigravity로 협업하더라도 프로젝트 파일과 변경 내용을 직접 확인
- **요구사항 → 작은 구현 → 자동 검사·실행 → 상태 기록 → 다음 작업** 흐름 유지
