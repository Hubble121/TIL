# 앱프로그래밍 3주차 배운 내용 정리

## 1. 객체지향 프로그래밍
- **클래스(Class)** : 데이터와 동작을 정의하는 설계
- **객체(Object)** : 클래스에 따라 생성된 실제 인스턴스
- **메시지(Message)** : 객체의 메서드를 호출하여 동작을 요청하는 것
- 객체를 설계할 때는 이름보다 **어떤 책임을 맡는지**를 먼저 판단

## 2. 객체의 책임과 코드 구조
- 객체는 자신이 관리하는 데이터와 그 데이터에 필요한 동작을 함께 다룸
- 예시 : `StudyGoal` 객체가 학습 목표의 완료 상태를 직접 관리
- 하나의 객체에 관계없는 기능을 지나치게 많이 넣지 않도록 주의

## 3. 상속과 다형성
- **상속(Inheritance)** : 기존 클래스의 특징을 이어받아 새로운 클래스를 정의
- **다형성(Polymorphism)** : 공통 타입을 통해 서로 다른 구현을 사용할 수 있는 성질
- Flutter의 `StatelessWidget`, `StatefulWidget` 등도 Widget 타입과 관련된 구조
- 공통 타입과 개별 구현의 역할을 구분해야 함

## 4. 캡슐화
- **캡슐화(Encapsulation)** : 객체의 내부 상태를 외부에서 무분별하게 변경하지 않도록 하고 정해진 메서드로 상태를 관리
- 내부 변수에 직접 접근하는 대신 `complete()`, `updateProgress()` 같은 행동을 제공
- Dart에서는 밑줄(`_`)로 시작하는 이름이 **라이브러리 단위 private** 접근 범위를 가짐
- `getter`를 통해 외부에 읽기 전용 값을 제공할 수 있음

## 5. 추상화와 인터페이스
- **추상화(Abstraction)** : 구현 세부사항보다 필요한 기능과 계약을 표현
- **인터페이스(Interface)** : 외부에서 사용할 수 있는 동작의 약속
- 예시 : `GoalRepository`는 목표를 불러오고 저장하는 기능을 정의하고, 저장 방법은 구현 클래스가 결정
- 구현체를 바꿔도 사용하는 쪽의 코드를 적게 수정할 수 있도록 구조화

## 6. 상속과 조합
- **상속** : 대상이 정말로 같은 종류이고 공통 성질을 공유할 때 검토
- **조합(Composition)** : 객체가 다른 객체의 기능을 받아 사용하는 방식
- 로깅 기능처럼 다른 역할은 상속보다 객체를 전달받아 조합하는 방식이 적절할 수 있음
- 재사용 자체보다 기능 변경에 대응하기 쉬운 구조인지 판단

## 7. Mixin과 클래스 수정자
- **Mixin** : 상속 계층을 늘리지 않고 여러 클래스에 공통 행동을 재사용
- Dart의 `with`를 이용하여 mixin의 동작을 적용
- **abstract** : 추상 클래스 정의
- **interface / implements** : 구현해야 할 계약
- **base / sealed** : 상속·구현 범위를 제어하는 클래스 수정자
- **final** : 외부 확장을 제한할 때 사용하는 수정자

## 8. KISS 원칙
- **KISS(Keep It Simple, Stupid)** : 불필요하게 복잡한 구조를 피하고 이해하기 쉬운 코드를 작성
- 조건과 책임이 뒤섞인 거대한 함수보다 역할이 분명한 작은 흐름을 선호

## 9. SOLID 원칙
- **S — 단일 책임 원칙(SRP)** : 한 클래스의 변경 이유를 하나의 책임에 집중
- **O — 개방·폐쇄 원칙(OCP)** : 기존 코드 수정은 줄이고 확장에 대응
- **L — 리스코프 치환 원칙(LSP)** : 하위 타입은 상위 타입의 계약을 지키며 대체 가능해야 함
- **I — 인터페이스 분리 원칙(ISP)** : 불필요한 기능에 의존하지 않도록 작은 계약으로 분리
- **D — 의존성 역전 원칙(DIP)** : 구체적인 구현보다 추상화된 계약에 의존

## 10. DRY와 YAGNI
- **DRY(Don't Repeat Yourself)** : 같은 지식이나 규칙이 여러 위치에 중복되지 않도록 관리
- **YAGNI(You Aren't Gonna Need It)** : 현재 필요하지 않은 기능을 미리 구현하지 않음
- 무조건 코드를 합치거나 복잡한 추상화를 추가하기보다 변경 이유와 요구사항을 먼저 고려

## 11. 요구사항과 인수 조건
- **사용자 목표** : 사용자가 해결하고 싶은 문제
- **요구사항** : 시스템이 제공해야 할 기능과 동작
- **책임 분리** : 어떤 객체와 기능이 각 요구사항을 담당할지 정함
- **인수 조건(AC, Acceptance Criteria)** : 구현이 완료되었는지 관찰 가능한 행동으로 판단하는 기준
- 막연한 기능 설명보다 입력·행동·기대 결과를 구분하는 것이 중요

## 12. 작은 기능 구현과 검증
- 큰 기능을 한 번에 만들기보다 핵심 기능부터 작게 구현
- 요구사항을 먼저 정리한 뒤 필요한 객체와 메서드로 역할 분리
- 정상 동작뿐 아니라 잘못된 입력과 경계 상황도 확인
- 기능 변경 이유와 검증 결과를 기록

## 13. 핵심 정리
- 좋은 객체는 이름보다 역할과 책임이 명확해야 함
- 캡슐화는 내부 상태를 보호하고 정해진 행동으로 변경을 관리
- 상속·조합·mixin은 재사용 목적과 변경 방향에 따라 선택
- KISS·SOLID·DRY·YAGNI는 복잡성을 줄이고 변경에 대응하기 위한 원칙
- 요구사항을 인수 조건으로 구체화해야 구현과 검증을 연결할 수 있음
