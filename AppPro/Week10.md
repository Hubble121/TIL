# 앱프로그래밍기초 10주차 배운 내용 정리

## 1. PRD와 개인 앱 개발
- **PRD(Product Requirements Document)** : 앱이 해결할 문제와 구현할 요구사항을 정리한 제품 요구사항 문서
- 9주차에 선정한 주제를 **구체적인 사용자 행동과 첫 화면**으로 연결
- 기능을 많이 만드는 것보다 **문서의 요구사항과 실제 구현이 일치하는지** 확인하는 것이 중요
- PRD는 한 번 작성하고 끝내는 문서가 아니라 구현·피드백에 따라 수정할 수 있음

## 2. 사용자 문제와 핵심 가치
- **사용자와 사용 상황** : 누가, 언제, 어떤 목적으로 앱을 사용하는지 설명
- **문제** : 사용자가 현재 어떤 어려움을 겪는지 정리
- **핵심 가치** : 앱을 사용한 후 무엇이 나아지는지 표현
- **사실** : 직접 경험·관찰·자료로 확인한 내용
- **가정** : 아직 확인되지 않은 불편이나 기대 효과
- **확인 질문** : 가정이 맞는지 알아보기 위해 확인할 사항
- 개인 경험을 모든 사용자에게 적용되는 사실로 일반화하지 않음

## 3. 수업용 PRD의 여섯 항목
1. **사용자와 사용 상황** : 대상과 이용 순간
2. **문제와 근거** : 확인한 사실·가정·확인 질문
3. **핵심 가치** : 사용자가 얻을 변화
4. **기능과 구현 범위** : 전체 기능과 이번 단계의 기능 구분
5. **첫 화면** : 보여 줄 정보·입력·버튼·사용자 반응
6. **완료 기준(AC)** : 어떤 행동과 결과를 확인할지
- 각 기능과 화면 요소를 PRD의 요구사항에 연결

## 4. 앱 전체 목표와 첫 구현 범위
- **전체 목표** : 최종적으로 제공하려는 앱의 기능과 가치
- **첫 구현** : 그중 지금 만들고 확인할 최소 화면과 행동
- **MVP** : 핵심 가치를 확인할 수 있는 최소한의 제품
- 실제 저장·로그인·서버 연결 등은 이번 구현에 필요한지 구분
- **예시 데이터·메모리 상태·실제 데이터 저장**은 서로 다른 수준의 구현

## 5. PRD에서 첫 화면으로 옮기기
- **화면 정보** : 앱 이름, 사용자에게 필요한 데이터와 안내
- **사용자 행동** : 입력·선택·버튼 등 핵심 조작
- **행동 후 반응** : 선택 내용 표시, 입력 결과, 상태 변화
- **빈 상태·잘못된 입력** : 정상 입력 외에 설명이나 예외 처리가 필요한 상황
- 화면을 위에서 아래 순서로 구상하고 요구사항 번호와 화면 요소를 연결

## 6. 인수 조건과 실행 결과
- **AC(Acceptance Criteria)** : 기능 완료를 관찰 가능한 행동과 결과로 판단하는 조건
- **입력/행동 → 기대 결과 → 실제 결과 → 판정** 순서로 기록
- 예 : 항목 선택 시 해당 내용 표시, 빈 입력 시 목록을 바꾸지 않고 안내
- **통과 / 실패 / 미실행**을 구분하고, 기대 결과를 실제 결과로 복사하지 않음
- 기능이 화면에 보이는 것뿐 아니라 실제 조작에 반응하는지도 확인

## 7. Flutter 프로젝트 생성과 실행
- **flutter doctor** : 개발환경 확인
- **flutter create** : 새 Flutter 프로젝트 생성
- **flutter run** : 실행 장치에서 앱 실행
- **flutter devices** : 연결된 실행 대상 확인
- **flutter analyze** : 정적 분석으로 코드 문제 확인
- 실행 중인 `flutter run`에서 지원되는 변경은 `r`로 Hot Reload 가능

```powershell
flutter doctor
flutter create my_first_app
cd my_first_app
flutter run
flutter analyze
```

## 8. AI를 이용한 PRD와 첫 화면 구현
- PRD 초안 요청에는 **주제·사용자·확인한 사실·가정·핵심 가치**를 전달
- 구현 요청에는 **검토한 PRD·화면 구상·현재 코드·실행 환경·완료 기준**을 제공
- **계획 검토 → 작은 범위 구현 → 분석·실행 → AC 확인** 순서로 진행
- 필요하지 않은 기능·패키지·서버를 임의로 추가하지 않도록 범위 지정
- AI가 제시한 결과와 본인이 실제 실행해서 확인한 결과를 구분

## 9. 수정과 오류 확인
- 오류가 나면 **입력·행동·기대 결과·실제 결과·오류 메시지·직전 변경**을 정리
- 한 번에 여러 문제를 수정하기보다 하나씩 원인을 찾고 같은 조건으로 재확인
- PRD와 구현이 달라졌다면 변경 이유와 남은 기능을 기록
- 코드 정적 분석, 자동 검사, 직접 화면 실행은 각각 다른 검증임

## 10. 개발 기록과 Git
- PRD와 첫 화면 구상은 프로젝트의 `docs/PRD.md`, `docs/first-screen.md` 등에 정리 가능
- `git diff`와 `git status`로 수정한 내용과 파일 확인
- 의도한 코드·문서만 커밋하고 실제 저장소 반영 여부 확인
- 구현·검증한 내용과 아직 미완료·미실행인 내용을 분리

## 11. 핵심 정리
- **사용자 문제 → 핵심 가치 → PRD → 첫 화면 → 구현·검증** 순서로 개발
- 전체 목표와 지금 구현할 범위를 구분
- 첫 화면의 정보·행동·반응을 PRD와 연결
- AI가 만든 코드도 직접 실행하고 인수 조건으로 확인
- 실제 결과를 근거로 문서와 다음 작업을 갱신
