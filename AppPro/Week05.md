# 앱프로그래밍 5주차 배운 내용 정리

## 1. 상태(State)와 상태관리
- **State** : 실행 중 변경될 수 있고, 화면에 영향을 주는 값
- 상태관리는 사용자의 입력이나 동작에 따라 값이 바뀌고, 그 변화가 화면에 반영되도록 관리하는 과정
- 화면에 보여 줄 값과 실제 저장된 상태가 서로 일치하도록 만드는 것이 중요

## 2. StatefulWidget과 State
- **StatefulWidget**
  - 실행 중 값이 바뀔 수 있는 화면의 틀을 정의
- **State**
  - 완료 여부와 같이 변경되는 값을 저장
- **build()**
  - 현재 상태값을 읽어 화면을 구성

### 역할 구분
- `StatefulWidget` → 바뀔 수 있는 화면의 구조
- `State` → 바뀌는 값 저장
- `build()` → 현재 값으로 UI 생성

## 3. setState()
- `State` 내부의 값을 변경했을 때 Flutter에 화면 갱신이 필요하다고 알려 주는 메서드
- 값만 변경하면 화면이 바로 바뀌지 않을 수 있으므로 상태 변경은 `setState()` 안에서 처리

```dart
setState(() {
  _done[index] = true;
});
```

- `setState()`가 호출되면 새로운 상태값을 이용해 화면을 다시 그릴 수 있도록 빌드가 예약됨

## 4. 이벤트 → 상태 변경 → UI 갱신
사용자의 동작이 화면에 반영되는 기본 흐름

1. 버튼의 `onPressed`와 같은 이벤트 발생
2. 이벤트에서 상태 변경 함수 실행
3. `setState()` 안에서 상태값 변경
4. `build()`가 현재 값을 읽어 화면을 다시 구성
5. `Text`, `Icon` 등의 Widget이 변경된 값을 표시

- 버튼은 눌렸는데 화면이 바뀌지 않는다면 이벤트, `setState()`, 화면에서 상태값을 읽는 부분을 순서대로 확인

## 5. 원본 상태와 계산값
- **원본 상태** : 다른 값에서 계산하지 않고 직접 저장하는 값
- **계산값(파생값)** : 저장된 원본 상태를 이용하여 계산할 수 있는 값

### 예시
- `_done` : 각 할 일의 완료 여부를 저장하는 원본 상태
- `_remaining` : `_done`에서 완료되지 않은 항목의 개수를 계산한 값

```dart
int get _remaining => _done.where((done) => !done).length;
```

- 계산할 수 있는 값을 다시 별도의 상태로 저장하면 두 값이 서로 달라질 수 있으므로 중복 저장을 피하는 것이 좋음

## 6. 상태 변화 확인
완료 여부를 토글하는 경우 상태와 화면은 같은 내용을 보여야 함

- 초기 상태 : `[false, false]` → 남은 할 일 `2`
- 첫 번째 완료 : `[true, false]` → 남은 할 일 `1`
- 다시 취소 : `[false, false]` → 남은 할 일 `2`

- 상태값을 변경한 뒤에는 화면의 표시와 계산값이 함께 변경되는지 확인해야 함

## 7. 프롬프트 엔지니어링
- AI에게 주는 요청의 **목표, 조건, 출력 형식**을 명확하게 설계하는 과정

### 요청에 포함할 내용
1. **목표** : 무엇을 만들 것인지
2. **조건** : 어떤 동작과 제약을 지켜야 하는지
3. **출력** : 결과를 어떤 형태로 설명하거나 제공할 것인지

### 예시
- 목표 : 완료 버튼 구현
- 조건 : 버튼을 다시 누르면 완료 상태가 취소되도록 구현
- 출력 : 수정한 코드와 변경 이유 설명

## 8. 컨텍스트 엔지니어링
- AI가 작업할 때 필요한 **자료, 도구, 조건, 실행 결과**까지 함께 설계하는 과정
- 프롬프트 엔지니어링은 컨텍스트 엔지니어링의 한 부분

### 컨텍스트 엔지니어링에 포함되는 내용
- 현재 코드와 프로젝트 자료
- 사용자 요구사항
- 수정 가능한 범위와 제약조건
- 공식 문서와 같은 근거 자료
- 실행 및 분석에 사용할 도구
- 작업 중 확인한 오류와 실행 결과

### 기본 흐름
1. 할 일과 범위 정하기
2. 필요한 코드와 자료 찾기
3. 실행 결과와 오류 확인하기
4. 새로 확인한 사실을 다음 작업의 컨텍스트에 반영하기

## 9. AI가 작업 전에 알아야 할 정보
AI에게 작업을 요청할 때 다음 내용을 명확하게 제공하면 불필요한 추측을 줄일 수 있음

- **목표** : 무엇을 완성할 것인가
- **현재 상태** : 현재 어떤 코드와 기능이 존재하는가
- **근거** : 어떤 자료를 기준으로 판단할 것인가
- **제약** : 어디까지 수정할 수 있는가
- **도구** : 무엇으로 실행하고 확인할 것인가
- **인수 조건(AC)** : 어떤 결과가 나오면 완료된 것인가

## 10. 자료별 역할 구분
작업에 사용하는 자료는 각각 확인하는 내용이 다름

- **사용자 요구 / 인수 조건** : 원하는 동작 확인
- **현재 코드** : 실제 변수와 코드 구조 확인
- **공식 문서** : Flutter API의 정확한 사용 방법 확인
- **실행 결과** : 현재 코드가 실제로 어떻게 동작하는지 확인

- 자료를 한꺼번에 많이 제공하는 것보다 현재 작업과 직접 관련된 내용을 먼저 선택하는 것이 중요
- 오류나 호출 관계가 다른 파일을 가리킬 때 필요한 범위를 추가로 확장

## 11. 구현 결과 검증
코드를 작성한 뒤에는 실제 결과를 확인해야 함

### 확인 방법
- 앱을 실행하여 화면과 동작 확인
- 상태값이 예상한 순서대로 변경되는지 확인
- `flutter analyze` 등을 이용해 코드 오류 확인
- 인수 조건과 실제 실행 결과 비교

### 예시 인수 조건
- 초기 남은 할 일 : `2`
- 완료 버튼 클릭 후 : `1`
- 다시 클릭하여 취소 : `2`

## 12. 핵심 정리
- 상태는 실행 중 변경되며 화면에 영향을 주는 값이다.
- `StatefulWidget`은 화면의 틀, `State`는 변경되는 값을 담당한다.
- 상태가 변경되면 `setState()`를 사용하여 Flutter에 화면 갱신을 알려야 한다.
- 화면은 저장된 상태를 기준으로 다시 구성되도록 작성한다.
- 계산할 수 있는 값은 별도의 상태로 중복 저장하지 않고 원본 상태에서 계산한다.
- AI에게 개발 작업을 요청할 때는 목표, 조건, 출력 형식을 명확히 작성한다.
- 컨텍스트 엔지니어링에서는 코드, 요구사항, 제약, 도구, 실행 결과 등을 함께 관리한다.
- 구현 후에는 실제 실행 결과와 인수 조건을 비교하여 기능이 제대로 동작하는지 검증한다.
