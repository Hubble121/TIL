# 앱프로그래밍기초 11주차 배운 내용 정리

## 1. 상태와 데이터 컨텍스트
- **데이터(Data)** : 앱에서 다루는 정보의 내용과 구조
- **상태(State)** : 현재 앱이나 화면에 표시되는 변경 가능한 값
- **데이터 모델(Data Model)** : 정보의 필드와 자료형, 관계를 표현하는 구조
- 현재 PRD·실제 코드·실행 결과를 비교하여 필요한 상태와 데이터를 결정
- 다른 예제의 필드를 그대로 복사하지 않고 자기 앱의 사용자 행동을 기준으로 설계

## 2. 사용자 행동과 상태 변경
- 기본 흐름 : **사용자 입력·선택 → 상태 변경 → 화면 갱신**
- 상태를 바꾸는 위치와 실제 화면에 사용하는 값을 구분
- 한 항목을 수정했을 때 다른 항목은 유지되는지 등 기대 결과를 확인
- 화면 변화뿐 아니라 어떤 데이터가 변경되는지도 함께 파악

## 3. 데이터 모델과 자료형
- 모델에는 현재 사용자 행동에 필요한 최소 필드를 지정
- **int** : 식별 번호, 개수, 정수 값
- **String** : 이름, 제목, 설명
- **bool** : 완료 여부, 선택 상태 등의 참·거짓
- 앱에 따라 `double`, `DateTime` 등도 사용할 수 있음
- 필요 없는 필드를 미리 추가하기보다 PRD 요구에 맞는 데이터 구조 선택

## 4. 엔티티(Entity)와 Dart 클래스
- **엔티티(Entity)** : 데이터 모델 중 식별자를 기준으로 개체를 구분하는 종류
- 값이 달라져도 같은 식별자를 가진 대상을 계속 동일한 개체로 다룰 수 있음
- **클래스(Class)** : 모델의 필드와 생성자 등을 정의하는 구조
- **생성자(Constructor)** : 객체 생성 시 전달받은 값으로 초기화
- 클래스가 있다고 모든 데이터 모델이 반드시 엔티티인 것은 아님

```dart
class StudyItem {
  final int id;
  final String title;
  final bool isDone;

  const StudyItem(this.id, this.title, this.isDone);
}
```

- 위 코드는 강의의 **공부 기록 앱 설명용 모델**이며 모든 학생이 동일한 앱을 만드는 것은 아님

## 5. 상태의 범위와 저장의 차이
- **화면 상태** : 특정 화면에서 사용하는 값
- **앱 상태** : 여러 기능이나 화면이 공유해야 하는 값
- **메모리 상태** : 앱 실행 중 유지되는 값으로 재시작 후 사라질 수 있음
- **영구 저장** : 파일·DB 등 앱을 다시 실행한 뒤에도 데이터가 남는 구조
- 화면에 값이 표시된다는 사실만으로 저장 기능이 구현된 것은 아님

## 6. 입력 조건과 불변식
- **입력 조건** : 사용자 입력이 허용되는 기준
  - 예 : 공백만 입력된 제목을 새 항목으로 추가하지 않기
- **경계 조건** : 빈 값, 0, 반복 클릭처럼 기능이 잘못될 수 있는 상황
- **불변식(Invariant)** : 앱의 정상 상태에서 항상 지켜져야 하는 규칙
  - 예 : 항목의 ID는 중복되지 않음, 다른 항목 수정 시 기존 값은 유지
- 조건을 정할 때 PRD의 **완료 기준(AC)**과 연결

## 7. setState()와 화면 갱신
- **StatefulWidget** : 변경 가능한 상태가 있는 화면을 구성하는 Widget
- **State** : 화면의 변경 가능한 값을 관리하는 객체
- **setState()** : 상태 변경 후 Flutter에 화면 재구성이 필요함을 알림
- 상태를 변경하는 코드와 화면을 다시 그리는 과정의 관계 이해
- 실제 저장 처리나 서버 통신을 `setState()`만으로 해결할 수는 없음

## 8. 정상·경계·반복 테스트
- **정상 사례** : 예상된 입력과 행동으로 원하는 결과가 나오는지 확인
- **경계 사례** : 빈 입력·잘못된 값·특수 조건에서 오류가 없는지 확인
- **반복 사례** : 같은 행동을 여러 번 해도 상태와 데이터가 일관적인지 확인
- **flutter analyze**와 앱 직접 실행 결과를 구분
- 확인 기록은 **입력·행동 / 기대 결과 / 실제 결과 / 통과·실패·미실행**으로 작성

## 9. AI를 이용한 코드 검토
- AI에게 PRD, 현재 코드, 필요한 모델·상태, 사용자 행동과 AC 제공
- 변경 계획을 먼저 확인하고 **필요한 파일과 기능만 수정**
- 실행하지 않은 코드는 완료로 단정하지 않음
- 오류 보고 시 입력값·동작 순서·에러 로그·실제 화면 등을 전달
- 상태와 데이터가 실제로 저장·갱신되는 위치를 직접 설명할 수 있어야 함

## 10. 12주차 중간발표 준비
- 발표 자료는 전체 **1~3쪽**으로 구성
- **앱 주제·해결하려는 문제·자신만의 핵심 가치**를 시각적으로 설명
- 사용 상황, 불편이 생기는 과정, 해결 전후 비교 또는 화면 구상 활용
- **15주차 최종 시연 목표**를 함께 제시
- 현재 구현 내용과 앞으로 만들 목표를 구분
- 자료를 보고 자기 말로 설명하는 **발표 연습** 필요

## 11. 개발 결과와 다음 작업
- 이번에 변경한 사용자 행동, 상태·데이터 구조, 확인한 사례 기록
- PRD와 실제 동작을 대조하고 미완료·실패·미실행 내용을 남김
- `git diff`로 변경 파일을 확인한 뒤 필요한 내용만 커밋
- 코드 구현 이력과 12주차 발표 준비 내용을 연결

## 12. 핵심 정리
- **데이터 모델은 정보의 구조**, **상태는 현재 변경되는 값**
- 입력과 상태 변화가 어떤 화면 결과로 이어지는지 이해
- 필요한 필드·자료형·불변식을 PRD의 행동과 연결
- **정상·경계·반복** 사례로 실제 동작 확인
- 12주차 발표에서는 구현 현황이 아니라 **사용자 문제와 핵심 가치**도 분명히 설명
