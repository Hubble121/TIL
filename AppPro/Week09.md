# 앱프로그래밍기초 9주차 배운 내용 정리

## 1. 개인 프로젝트 주제 선정과 분석
- **목표** : 사용자 문제를 찾아 개인 Flutter 앱의 주제와 구현 범위를 결정
- **7주차 제안서**를 출발점으로 활용하되, 조사 결과에 따라 주제를 유지하거나 변경
- 학습 활동은 **문제·사용자 정의 → 후보 검토 → 기능 범위 → 인수 조건 → 다음 작업**으로 연결
- 수업은 설명 30분과 실습 150분으로 구성되며, **본격적인 코드 구현은 10주차부터 시작**

## 2. 사용자·상황·문제 정의
- **사용자** : 앱의 핵심 기능을 사용할 대상
- **사용 상황** : 사용자가 언제·어디서·왜 앱을 필요로 하는지
- **현재 해결 방식** : 사용자가 기존에 문제를 해결하려는 방법
- **불편과 핵심 가치** : 현재 방식의 어려움과 앱 사용 후 얻을 도움
- 자신의 경험과 실제 관찰을 구분하고, 확인되지 않은 부분은 가정으로 남김

## 3. 5W1H와 JTBD
- **5W1H** : 누가, 언제, 어디서, 무엇을, 왜, 어떻게의 질문으로 주제 후보 구체화
- **JTBD(Jobs To Be Done)** : 사용자가 특정 상황에서 이루려는 일을 중심으로 문제 분석
- 기능 이름부터 결정하지 않고 사용자의 **상황 → 하려는 일 → 현재 방법 → 불편 → 기대 효과**를 파악
- 후보 3개 등을 비교하며 실제로 설명·확인할 수 있는 문제를 우선 선택

## 4. 유사 앱 조사
- 기존 앱의 공개 화면, 기능 소개, 실제 동작을 확인
- **직접 관찰한 사실 / 해석·추정 / 미확인 정보**를 구분하여 기록
- 공식 링크, 확인 날짜, 화면·행동·결과와 참고할 점을 남김
- 유사 앱에 기능이 많더라도 전부 그대로 따라 만들 필요는 없음

## 5. MoSCoW 우선순위
- **Must** : 이번 버전에서 반드시 필요한 기능
- **Should** : 중요하지만 상황에 따라 조정할 수 있는 기능
- **Could** : 시간이 충분하면 구현할 기능
- **Won't this time** : 이번 구현 범위에서 제외할 기능
- 기능의 필요성뿐 아니라 선행 조건과 개발 부담을 함께 판단

## 6. KISS와 YAGNI
- **KISS** : 구현을 불필요하게 복잡하게 만들지 않기
- **YAGNI** : 현재 요구되지 않은 미래 기능을 미리 만들지 않기
- 단순화는 중요한 동작을 빠뜨리는 것이 아님
- 이번 학기의 개발 시간·기술·저장 방법·외부 의존성을 고려하여 범위 결정

## 7. MVP와 핵심 사용자 흐름
- **MVP** : 핵심 사용 가치를 확인할 수 있는 최소한의 앱 버전
- 사용자 흐름을 **시작 → 입력·행동 → 결과 확인** 순서로 표현
- 필수 기능뿐 아니라 초기 화면, 목록, 데이터 구조, 오류·빈 상태 처리도 고려
- 기능 범위를 초과하는 로그인·서버·외부 API 등은 필요한 근거가 있을 때만 포함

## 8. 인수 조건(AC)과 검증
- **인수 조건(Acceptance Criteria)** : 기능을 올바르게 만들었는지 관찰 가능한 행동으로 판단할 기준
- 예 : 항목 입력 후 목록 표시, 빈 입력 시 안내, 완료 표시 변경, 항목이 없을 때 빈 화면 안내
- **계획된 AC**와 **실제 실행하여 확인한 결과**는 구분해야 함
- 아직 구현하지 않았다면 검증 결과를 성공으로 표시하지 않음

## 9. AI 협업과 학생의 판단
- AI는 주제 후보·분석·비교를 도울 수 있지만 **선택과 근거 기록은 학생의 역할**
- 요청 시 목표, 이미 결정한 내용, 기술 제약, 미확인 정보와 제외 범위를 전달
- 제안서·실제 관찰·추정·실행 결과를 구분하고 다음 단계에 반영
- 교수님이 확인한 내용과 AI가 추천한 내용을 혼동하지 않음

## 10. 9주차 실습과 제출 결과물
- **주제 정리** : `week09/topic.md` — 앱 주제, 사용자·문제, 기능, 화면, 저장 방식, AC와 확인 결과
- **분석 기록** : `week09/analysis.md` — 후보 비교, JTBD, 유사 앱 조사, 선택·제외 이유와 피드백
- 화면 스케치와 개인 GitHub 저장소·커밋 링크 포함
- 교수님 확인 상태는 **확정 / 조건부 확정 / 재선정 필요 / 미확인** 등으로 구분
- **10주차 첫 작업** : 만들 화면과 핵심 행동 하나, 관련 AC를 정하고 개발 준비

## 11. 핵심 정리
- **사용자 문제 → 조사·근거 → 우선순위 → MVP·AC → 교수님 확인 → 구현 준비** 흐름
- 5W1H·JTBD는 문제 파악, MoSCoW·KISS·YAGNI는 범위 결정에 활용
- 실제 조사·교수님 확인·코드 실행을 하지 않았다면 그 결과를 임의로 기록하지 않음
- 9주차는 주제 선정과 분석 중심이며 **구현은 10주차부터 진행**
