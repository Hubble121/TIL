# 앱프로그래밍기초 7주차 배운 내용 정리

## 1. 개인 앱 기획의 기본 개념
- **문제** : 사용자가 특정 상황에서 겪는 불편
- **핵심 가치** : 앱 사용 후 사용자가 얻게 되는 중요한 도움
- **MVP(Minimum Viable Product)** : 핵심 가치를 확인할 수 있는 최소한의 제품
- **제약** : 개발 시 지켜야 할 시간·기술·환경·자료 등의 조건
- **인수 조건(AC, Acceptance Criteria)** : 기능이 기대대로 동작하는지 판단할 수 있는 기준
- 기능을 먼저 늘리기보다 **누구의 어떤 문제를 해결하는지** 정의하는 것이 중요

## 2. 앱 기획의 과정
1. **문제 찾기** : 누구에게 어떤 불편이 있는지 정리
2. **범위 정하기** : 이번 버전에서 구현할 핵심 기능 선택
3. **확인 기준 설정** : 기능이 완료되었는지 확인할 방법 작성
4. **자료 선택** : 현재 작업에 필요한 코드와 문서 선택
5. **검증·갱신** : 실제 결과를 바탕으로 계획과 자료 수정

## 3. 사용자와 문제 정의
- **대상** : 앱을 실제로 사용할 사람
- **사용 순간** : 사용자가 앱을 필요로 하는 시점
- **현재 방법** : 사용자가 지금 문제를 해결하는 방식
- **불편** : 현재 방법으로 해결하기 어려운 부분
- **사용자 스토리(User Story)** : **누가 / 무엇을 / 왜**의 구조로 사용자 목표 표현
- 해결할 문제가 명확하지 않은데 기능만 정하면 앱의 목적이 흐려질 수 있음

## 4. MVP와 기능 우선순위
- 첫 버전은 사용자가 핵심 행동을 할 수 있는 최소 범위에 집중
- **필수 기능** : 공부 항목 추가, 오늘 목록 확인, 완료 여부 표시
- **다음 버전 후보** : 날짜별 기록, 알림, 검색
- **현재 버전에서 제외** : 로그인, 서버 저장, 친구 순위
- 추가 기능이 있어야만 더 좋은 MVP가 되는 것은 아님

## 5. 개발 제약과 제외 범위
- **실행 환경** : 수업에서 확인한 Flutter 개발환경
- **시간과 인원** : 학생 한 명이 단계별로 개발하는 상황
- **기술 범위** : 배운 Widget과 상태 처리 방법부터 사용
- **데이터 범위** : 가상의 공부 항목을 이용한 첫 버전
- **외부 의존성** : 첫 버전은 계정·서버·유료 API 없이 구성
- 제외한 기능도 기획 문서에 적어 구현 범위를 명확히 하는 것이 중요

## 6. 인수 조건(AC)
- 기능의 완료 여부를 **행동과 관찰 가능한 결과**로 확인
- **AC1 · 제목을 입력해 추가** : 입력한 공부 항목이 목록에 나타남
- **AC2 · 빈 제목 제출** : 안내가 표시되고 목록은 그대로 유지됨
- **AC3 · 완료 표시 선택** : 선택한 항목의 완료 상태가 변경됨
- **AC4 · 항목이 하나도 없음** : 빈 목록에 대한 안내가 표시됨
- **입력 / 행동 / 기대 결과**를 분리하고, 구현하지 않은 조건을 성공했다고 기록하지 않음

## 7. 화면 구성과 데이터 모델
- **화면(UI)** : 입력 영역, 오늘 목록, 추가 버튼, 완료 표시, 안내 메시지
- **상태(State)** : 현재 목록과 각 항목의 완료 여부 등 변경되는 값
- **데이터 모델(Model)** : 화면에 필요한 공부 항목의 구조
- 화면은 사용자 입력을 받고, 상태는 값을 관리하며, 데이터 모델은 항목의 형태를 정함

### 강의자료의 데이터 모델 예시
```dart
class StudyItem {
  final int id;
  final String title;
  final bool isDone;

  const StudyItem(this.id, this.title, this.isDone);
}
```

- **id** : 항목을 구분하는 값
- **title** : 공부 항목 제목
- **isDone** : 완료 여부
- 사용자 행동 → 상태 변경 → 화면 반영의 연결 관계를 이해

## 8. 화면 상태와 예외 처리
- **항목 없음** : 아직 기록한 공부가 없다는 안내
- **항목 있음** : 공부 제목과 완료 여부 표시
- **빈 입력** : 제목 입력을 요청하는 안내
- **외부 요청을 추가한 경우** : 로딩·성공·실패 결과의 표시 방법 고려
- 정상 동작뿐 아니라 빈 값과 오류 상황도 인수 조건으로 확인

## 9. 설계 결정 기록(ADR)
- **ADR(Architecture Decision Record)** : 설계 선택의 배경과 영향을 기록하는 문서
- **상황** : 짧은 시간 안에 핵심 흐름을 검증해야 함
- **선택지** : 메모리 목록 / 기기 저장 / 서버 저장
- **결정** : 첫 버전은 메모리 목록으로 시작
- **영향** : 재시작하면 사라지는 점을 안내하고 저장 기능은 추후 검토
- 어떤 방법을 선택했는지뿐 아니라 **선택하지 않은 이유**도 남김

## 10. 개발 규칙과 품질 확인
- **lowerCamelCase** : 변수와 함수 이름에 사용하는 표기 방식
- **입력 규칙 재사용** : 같은 입력 처리 기준을 여러 화면에서 일관되게 적용
- **코드와 화면 함께 확인** : 코드 변경 후 예상한 동작이 실제 화면에 나타나는지 검증
- **flutter analyze** : 정적 분석을 위한 명령어
- 정적 분석 결과와 실제 실행 결과는 서로 다른 검증 자료이므로 구분

## 11. 프롬프트 엔지니어링
- **프롬프트 엔지니어링** : AI에게 목표·조건·기대 결과를 명확히 전달하는 방법
- 막연한 요청보다 **기능, 인수 조건, 수정 범위, 확인 방법**을 함께 제시
- 예시 : '입력 검사를 추가해 줘'보다 'AC2를 만족하도록 빈 제목 입력을 거부하고 목록이 유지되는지 확인해 줘'가 구체적
- 요청 범위를 벗어나는 저장·계정 기능 등을 임의로 추가하지 않도록 제약 명시

## 12. 컨텍스트 엔지니어링
- **컨텍스트(Context)** : 현재 요청을 판단하는 데 필요한 지시·자료·도구·결과·이력
- **컨텍스트 엔지니어링** : 작업에 필요한 정보를 선택·구성하고 결과에 따라 갱신하는 방법
- 프롬프트는 '어떻게 지시할 것인가', 컨텍스트는 '지금 무엇을 참고하게 할 것인가'에 초점
- **최신성** : 현재 코드와 기획에 맞는 자료인지 확인
- 관련 없는 오래된 자료를 한꺼번에 넣지 않도록 주의

## 13. 작업 컨텍스트의 다섯 요소
1. **목표** : 이번 작업에서 구현하거나 검토할 것
2. **근거** : 제안서·현재 코드·확인한 문서
3. **제약** : 변경하면 안 되는 구조와 제외할 기능
4. **현재 상태** : 무엇이 구현되었고 무엇이 미완료인지
5. **확인 기준** : 실행 결과로 무엇을 확인할지
- AI가 추정한 정보와 사용자가 제공한 사실을 구분

## 14. 자료의 출처와 충돌 처리
- **기능 범위** : 최신 제안서의 MVP·인수 조건 확인
- **입력 구현** : 현재 코드에서 실제로 사용되는 방식 확인
- **API 사용법** : 공식 문서와 현재 버전 확인
- **검증 결과** : 실행 로그와 오류 기록 확인
- 자료가 충돌하면 최신 승인된 기준을 확인하고, 임의로 한쪽 내용을 사실로 확정하지 않음

## 15. 도구 계약과 검증 기록
- **도구의 목적** : 무엇을 확인하거나 변경하려는가
- **입력·출력** : 어떤 자료를 전달하고 어떤 결과를 받는가
- **권한** : 파일 읽기·수정·실행 중 무엇이 허용되는가
- **실패** : 결과 없이 실패했는지, 어떤 오류가 발생했는지
- **검증 기록** : 입력·행동·기대 결과·실제 결과를 다시 확인할 수 있게 남기는 기록
- **계획 / 구현 / 검증 / 피드백 / 갱신**의 순서로 작업을 발전시킴

## 16. 다음 작업과 개인정보 보호
- 검증 결과에 따라 기존 계획과 다음 작업에 필요한 자료를 갱신
- 실제로 완료한 작업과 미정인 문제를 구분하여 기록
- 실명·연락처 대신 실습용 가상 데이터 사용
- 비밀번호·토큰·API 키 등은 AI 요청이나 공개 문서에 포함하지 않음
- 작업 목적에 따라 읽기·수정·배포 권한을 구분

## 17. 핵심 정리
- **문제 → 사용자 → 핵심 가치 → MVP → 인수 조건**의 흐름으로 앱 기획
- 첫 버전은 공부 항목 추가·목록·완료 표시 등 최소 기능에 집중
- 화면·상태·데이터 모델의 역할을 구분하고 변경 흐름을 확인
- ADR로 설계 선택의 이유와 영향을 기록
- 컨텍스트 엔지니어링은 현재 목표에 필요한 자료를 골라 AI에게 제공하고 갱신하는 과정
- 구현 여부는 추정하지 않고 실제 실행 결과와 인수 조건을 근거로 확인
